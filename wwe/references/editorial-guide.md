# 기술 문서 작성·윤문 기준과 WWE 개정 참고

2026-10-05 `study-hugo` 게시글 재작성에서 적용한 판단 기준을 정리했다. Claude에 초안 작성을 맡길 때 참고하고, WWE의 다음 버전에서 지침과 평가 사례를 보완하는 데 사용한다.

목표는 독자가 문제와 근거를 따라가며 결론이 어떤 조건에서 성립하는지 이해하게 하는 것이다. 문장 표현뿐 아니라 설명 순서, 중복, 수치의 의미, 근거와 결론의 연결을 함께 본다.

## 현재 지침과의 관계

현재 실행 규칙은 [SKILL.md](../SKILL.md), [구조 편집 가이드](structure-editing.md), [한국어 명확성 지침](korean-clarity.md)에 있다. 이 문서는 적용 사례와 개정 제안을 담은 참고 자료이며, 편집 경로·게이트·호출 예산을 변경하지 않는다. v1.7.1은 이 문서를 추가한 패치 버전이다.

신규 문서를 작성할 때는 아래 기준으로 설명을 구성한다. 기존 문서의 윤문에서는 사용자가 허용한 범위를 따른다. 문장만 고치는 요청에 구조 변경을 적용하지 않으며, 전면 재작성이 허용돼도 사실·근거·기술적 의미는 보존한다. 전사와 원자료는 기록의 성격과 지정된 편집 범위를 먼저 확인한다.

## 구조까지 다시 쓴 이유

개별 문장이 자연스러워도 같은 결론이 서론·본문·요약·근거 표에 반복되거나, 설정을 고른 이유가 코드 뒤에 나오면 읽는 흐름이 끊긴다. 측정 조건이 멀리 떨어져 있으면 독자가 제한된 결과를 일반적인 효과로 받아들일 수도 있다. 이런 문제는 문단의 역할과 순서를 함께 바꿔야 해결된다.

이번 검토 대상은 신규 17편과 본문을 수정한 기존 4편이었다. 19편은 본문과 구조를 재작성했고, 전사·STT 2편은 안내를 편집하며 기록 본문을 보존했다. 모든 글에 같은 구조를 적용하거나 일정 비율만큼 분량을 줄이지 않았다.

## 판단 기준과 실제 적용 사례

아래 사례는 작업 기록을 요약한 것이다. 따옴표로 표시한 명칭 외의 설명은 실제 문장의 전후 인용문이 아니다.

| 판단 기준 | 편집할 때 확인한 것 | 이번 작업의 사례 |
|---|---|---|
| 이해에 필요한 순서 | 다음 설명을 이해하려면 어떤 전제와 선택 이유를 먼저 알아야 하는가 | Vector·ClickHouse 글에서 직접 sink와 OTel exporter 비교를 설정 코드 앞에 배치했다. |
| 절과 문단의 역할 | 각 절이 다른 질문에 답하는가. 중복을 합쳐도 고유한 근거가 남는가 | 스토리지 글의 본문과 중복 근거 행, 절마다 반복한 ‘바뀐 것 / 남은 비용 / 적용할 수 없는 비교’를 정리했다. |
| 주장과 적용 조건 | 수치의 대상·분모·기간이 드러나는가. 실측·추정·계획이 구분되는가 | vmagent의 실측과 전체 적용 예상을 구분하고, vmstorage의 전체 감축 재집계와 실제 적용 계획을 나눴다. |
| 근거에 맞는 주장 강도 | 예외가 결론에도 반영됐는가. 현재 상태와 정책 또는 계획을 구분했는가 | NFS 최종 판단표를 본문의 제한에 맞췄다. hub/edge 글은 home-assistant의 PVC 예외를 앞에서 밝혔다. |
| 인과관계의 보존 | 각각 확인된 두 사실을 근거 없이 원인과 결과로 연결하지 않았는가 | 독립 의미 검토에서 초안에 새로 붙은 인과 3곳을 제거했다. LeapIO 수치에는 ‘논문 초록이 제시한 개발 동기’라는 한정을 복원했다. |
| 정보에 맞는 표현 형식 | 연속된 설명은 문단으로, 절차는 순서대로, 병렬 비교는 표나 목록으로 읽히는가 | 필요한 비교표와 절차는 유지하고 형식적인 도입·반복 결론을 줄였다. |
| 명확한 한국어 | 주체·대상·조건·동작이 드러나는가. 조사와 서술어를 줄이면서 관계를 잃지 않았는가 | 관계가 생략된 명사 나열을 풀고 습관 표현을 문맥별로 검토했다. 실제 UI 명칭과 기술 용어는 보존했다. |

근거 표에는 측정 환경·방법·고유 수치·제약처럼 본문 판단을 확인하는 데 필요한 정보가 있어야 한다. 같은 설명을 되풀이하는 행을 합칠 때도 주장과 출처의 연결은 남긴다. 표 자체를 없애거나 반복 횟수를 일정 수준 이하로 만드는 것이 목표는 아니다.

“핵심은”, “한눈에”, “정리하면” 같은 표현도 문맥에서 기능을 판단한다. 실제 대시보드 명칭인 ‘한눈에’는 유지했다. ‘카테고리를’와 ‘유실은’에서 잡힌 부분 문자열은 교정 대상으로 보지 않았다. “다만”, “반면”이 실제 제한이나 대조를 나타내면 그 관계를 살린다.

## Claude에 전달할 작성 지침

다음 블록을 문서 작성 요청에 함께 사용할 수 있다. 기존 문서의 편집 범위와 원문 보존 조건은 요청별로 명시한다. 이 블록을 추가하는 것만으로 WWE에 신규 작성 실행 모드가 등록되지는 않는다.

```text
기술 문서를 작성하거나 윤문할 때 다음 기준을 따른다.

1. 작성 전에 독자의 상황, 해결하려는 질문, 핵심 주장과 근거를 파악한다.
   이 준비 항목을 그대로 서론이나 목차에 나열하지 않는다.

2. 도입부에는 실제 문제와 필요한 배경을 제시한다.
   독자가 이해하는 데 필요한 순서로 설명한다.
   선택의 이유와 전제는 그에 의존하는 설정·코드·결론보다 먼저 설명한다.

3. 각 절은 구분되는 질문에 답하게 한다.
   서론, 본문, 요약, 근거 표에서 같은 설명을 반복하지 않는다.
   중복을 합칠 때 고유한 수치, 조건, 예외, 출처를 보존한다.

4. 측정 결과, 계산한 예상치, 문서에 명시된 사실, 출처의 주장,
   작성자의 추론, 미검증 계획을 구분한다.
   수치와 결론 가까이에 해석에 필요한 대상·기간·버전·분모·조건을 적는다.

5. 원문이나 자료에 없는 경험, 선택 이유, 인과관계, 검증 결과를 만들지 않는다.
   불확실하거나 서로 충돌하는 정보는 임의로 확정하지 않는다.
   가능한 효과를 보장되는 결과로 강화하지 않는다.

6. 현재 운영 상태, 과거 구성, 제안하는 변경을 구분한다.
   코드와 명령어가 어느 상태에 해당하는지 실행 예시 앞에서 설명한다.

7. 이어지는 논리는 문단으로, 실행 순서는 번호 목록으로,
   동일한 기준의 비교는 표로 표현한다.
   글의 목적에 맞게 선택하며 동일한 목차·절별 요약·결론 형식을 강제하지 않는다.

8. 구체적인 주체와 동작이 드러나는 자연스러운 한국어를 사용한다.
   의미가 불분명한 명사 나열과 추상적인 표현을 풀어 쓴다.
   상투적인 강조와 정리 문구는 기능이 없을 때 제거한다.
   특정 단어의 일괄 금지나 기계적인 동의어 교체는 하지 않는다.

9. 문장 수, 문단 길이, 분량 감소를 품질 목표로 삼지 않는다.
   이해와 판단에 필요한 설명과 제약을 충분히 남긴다.
   마지막 요약은 판단 기준이나 다음 행동을 제공하는 데 도움이 될 때 사용한다.

10. 작성 후 가독성 검토와 사실·의미 검토를 분리한다.
    추가된 인과관계, 강해진 단정, 빠진 조건, 반복 설명을 확인한다.
    기존 문서에서는 허용된 범위만 편집하고 원문과 대조한다.
    코드·인용·식별자·수치·출처를 보존하고, 확인한 오류를 고치면 근거를 기록한다.
    사이트 문서의 제목이나 구조를 바꾸면 실제 렌더링과 기존 링크도 확인한다.
```

## 다음 버전에서 보완할 항목

대부분의 원칙은 현행 지침에 이미 있다. 개정에서는 규칙을 늘리기 전에 실제 실패를 재현할 수 있는 예시와 검토 질문을 보강한다. 아래는 반영 제안이며 구현되거나 검증된 변경 사항이 아니다.

| 보완할 부분 | 현재 연결할 지침 | 다음 개정에서 확인할 결과 |
|---|---|---|
| 새로 만들어진 인과관계 | `korean-clarity.md`의 문장 성분 복원, `structure-editing.md`의 내용 대조 | 문장 연결이 매끄러워져도 원문에 없는 원인·선택 동기가 생기지 않는다. |
| 수치의 비교 범위와 적용 상태 | `structure-editing.md`의 주장·근거 대조 | 실측·계산·예상과 현재·과거·미검증 상태가 수치 및 코드 가까이에서 구분된다. |
| 본문과 결론의 주장 강도 | `structure-editing.md`의 전제·예외 보존 | 요약이나 판단표가 본문의 제한을 생략하며 보편적인 권고로 바뀌지 않는다. |
| 문서 간 반복과 형식 선택 | `structure-editing.md`의 관련 글 읽기, 장르별 전개 | 반복을 줄인 뒤에도 비교표·절차·원자료처럼 필요한 형식과 정보가 남는다. |
| 탐지 결과의 문맥 판정 | `korean-clarity.md`의 용어 보존과 접속사 우선순위 | 실제 UI 명칭·기술 용어·인용·부분 문자열 오탐을 일괄 치환하지 않는다. |

상세 사례는 이 참고 문서나 평가 자료에 두고, 공통 실행 지침에는 필요한 판단 기준과 해당 자료의 연결만 남기는 편이 좋다. 같은 규칙을 여러 파일에 복제하면 다음 수정 때 서로 어긋나기 쉽다. 신규 작성 경로의 정식 도입 여부와 버전 번호는 후속 개정에서 결정한다.

### 평가에 사용할 짧은 사례

다음 입력은 위 실패 유형을 확인하기 위해 새로 만든 예시다. 특정 완성 문구와 일치하는지를 채점하지 않고, 결과가 보존해야 할 의미를 확인한다.

| 예시 입력 | 결과에서 확인할 의미 |
|---|---|
| “구성을 변경했다. 이후 전송량을 측정했다.” | 측정 결과 때문에 구성을 변경했다는 동기가 새로 생기지 않는다. |
| “시험 환경에서 전송량이 40% 감소했다. 전체 적용 시 비용은 8% 감소할 것으로 계산했다.” | 측정 대상과 예상 대상, 전송량과 비용, 실측과 계산이 구분된다. 두 비율은 이 평가용 가상 수치다. |
| “이 경로는 장애 전환을 위해 설계했다. 정상 경로만 시험했다.” | 장애 전환까지 검증했다는 문장이 생기지 않는다. |
| “동기 쓰기 조건에서 비교했다. 캐시 설정이 다른 환경은 시험하지 않았다.” | 결론이나 표에서도 해당 조건과 미검증 범위가 유지된다. |
| “본문과 요약에 같은 결론이 있고, 근거 표에만 측정 버전이 있다.” | 중복을 합쳐도 유일한 측정 버전과 출처 연결이 남는다. |
| “대시보드의 ‘한눈에’ 행을 확인한다. 다만 이 행은 실시간 집계가 아니다.” | 실제 UI 명칭과 갱신 시점에 대한 제한을 보존한다. |

평가는 장애 기록·설정 안내·비교 문서처럼 목적이 다른 원문에서도 수행한다. 구조 변경이 허용된 요청과 문장만 수정하는 요청을 각각 확인한다. 큰 개정에서는 편집자와 별도의 검토자가 원문·후보를 대조하는 방식이 유용하지만, 짧은 문장 교정마다 추가 호출을 의무화하지는 않는다.

## 검증 결과를 해석할 때

이번 작업은 내용 대조와 사이트 검증을 함께 수행했다. 기존 HTML ID 356개 보존, 내부 링크 검사, Hugo 빌드, 회귀 테스트 17개 통과는 렌더링과 기존 동작의 확인 근거다. 글의 모든 기술 사실을 새로 실험했다는 뜻은 아니다.

Claude 백필 기록은 총수 5,065개와 항목별 합계 5,064개가 달랐다. 원자료로 확정할 수 없어 값을 임의로 맞추지 않고 재확인 필요를 표시했다. 이후 개정에서도 미확인을 유지하는 판단을 정당한 결과로 평가한다.

지문 점수, 금지 표현 개수, 글자 수 감소, 빌드 성공만으로 윤문 품질을 판정하지 않는다. 핵심 주장·근거·전제·예외가 남았는지와 설명 순서가 독자의 이해를 돕는지를 함께 검토한다.
