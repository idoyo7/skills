# 문장 윤문으로 해결되지 않는 글을 다시 구성하기

이 경로는 사용자가 문단·소제목·전개 순서까지 다시 쓰도록 요청했을 때 사용한다. 원문의 기술적 의미와 근거를 지키면서 설명 순서를 바꾸는 편집이다. 사실 조사, 제품 선택, 정책 변경을 새로 맡았다는 뜻은 아니다.

## 기존 파이프라인이 남기는 문제

v1.4까지의 기본 파이프라인은 안전한 문장 윤문에 맞춰져 있다. 다음 제약은 참조 문서를 보호하지만, 글 자체가 잘못 구성됐을 때는 그 구성을 고정한다.

| 기존 제약 | 구조 편집에서 막히는 작업 |
|---|---|
| 헤딩·불릿 수와 순서·표·문단 구조 보존 | 중복 절 합치기, 목록을 인과관계가 있는 산문으로 쓰기, 비교 가치 없는 표 풀기 |
| L13 콜론 유도·L14 헤딩 형태 등 구조 지표를 report-only로 처리 | 모든 절이 같은 “정의: 설명” 형태로 전개되는 문제를 발견해도 본문은 유지 |
| 게이트 S의 확신·필러·미검증 판정을 보고만 함 | 근거와 주장을 떨어뜨린 문단, 무의미한 도입과 반복 결론을 그대로 둠 |
| 파일당 1콜 상한과 파일별 순차 처리 | 관련 글 전체의 반복, 문서 간 역할 중복, 긴 글의 논증 순서를 충분히 다루기 어려움 |
| 지문 점수 하락을 채택 조건으로 사용 | 장식만 지워도 통과할 수 있고, 필요한 비교표가 점수를 높일 수도 있음 |

`정밀 모드`는 기존 파이프라인의 재시도 횟수를 늘린다. 그것만으로 구조 보존 제약이 해제되지는 않는다. `md_shield.py verify --allow-restructure` 역시 아래의 의미·출처·사이트 전체 링크 검증을 대신하지 못한다.

이 경로에서는 Phase 0~9의 마스킹·복원·게이트 A~D/S·파일당 콜 상한을 적용하지 않는다. `docs-profile.md`를 프롬프트에 섞지 않는다. 현재 에이전트가 원문 전체를 읽고 편집하며, humanize-korean 설치를 이 경로의 선행 조건으로 요구하지 않는다. 사용자가 직접 정한 예산·수정 범위·검토 전용 조건은 지킨다.

사용자가 Claude 준비 후 Astra 최종 퇴고를 선택했다면 [handoff 가이드](engine-swap-astra.md)를 함께 따른다. Claude는 원본·초안·검사 메모를 준비하고 Astra high가 최종 문체를 결정한다. 아래 내용 보존·재개·사이트 검증은 그대로 적용하며, Claude는 검증에서 발견한 문제를 근거와 함께 Astra에 돌려보낸다. 이미 Astra가 편집을 맡은 실행 안에서는 다시 Codex를 호출하지 않는다.

## 원문에서 독자가 해결하려는 일을 찾기

대상 파일 전체와 이어지는 글을 읽는다. 문서가 많으면 각 글이 답하는 질문과 연결만 짧게 적어 중복을 비교한다. 단어 출현 횟수만으로 내용을 없애지 않는다. 제품명과 설정 키가 여러 글에 반복되는 것은 자연스럽다.

편집 메모에는 다음을 짧게 남긴다. 이것을 게시글의 필수 서론이나 고정 목차로 출력하지 않는다.

- 독자는 어떤 상황에서 이 글을 찾으며, 읽고 나서 무엇을 판단하거나 실행해야 하는가.
- 글의 주장은 무엇이며, 원문 어디의 로그·코드·수치·출처가 뒷받침하는가.
- 설명에 앞서 필요한 조건과 이미 다른 글에서 설명한 내용은 무엇인가.
- 독자가 다음 내용을 이해하려면 앞에서 무엇을 알아야 하는가.

“이 글에서는 A·B·C를 살펴본다” 같은 안내보다 실제 문제와 조건으로 시작할 수 있는지 본다. 원문의 판단 근거가 뒤에 묻혀 있으면 근거와 주장을 가까이 옮긴다. 약어 정의를 전부 앞에 모으지 말고 필요한 위치에서 설명한다.

## 글의 종류에 맞춰 순서를 고르기

다음은 선택 가능한 전개 예시다. 모든 글에 적용하거나 항목 수를 맞추지 않는다. 한 글 안에서도 장애 기록과 설정 레퍼런스가 함께 필요할 수 있다.

| 글의 목적 | 선택 가능한 순서 | 편집할 때 확인할 점 |
|---|---|---|
| 장애 기록 | 증상과 영향 → 관측한 증거 → 원인 → 수정과 재검증 | 처음부터 원인을 알았던 것처럼 경험을 다시 만들지 않는다. 해결 과정에 의미 없는 시행착오 나열은 줄인다. |
| 의사결정 | 요구와 제약 → 선택지의 실제 차이 → 채택 근거 → 결정을 바꿀 조건 | 모든 대안을 같은 분량으로 설명할 필요는 없다. 제외한 이유와 비용 가정을 남긴다. |
| 튜토리얼 | 도달할 결과와 환경 → 필요한 순서대로 실행 → 결과 확인 → 자주 만나는 실패 | 실행 의존 순서를 문장 리듬 때문에 바꾸지 않는다. 개념 설명은 해당 명령 가까이에 둔다. |
| 레퍼런스 | 찾으려는 작업·설정별 항목 → 기본값·범위·제약 → 관련 예시 | 표와 반복 형식이 탐색에 도움이 되면 유지한다. 에세이처럼 읽히도록 강제로 풀지 않는다. |

## 절과 문단을 다시 쓰기

각 절이 독자의 다른 질문에 답하는지 확인한다. 같은 답을 서두 콜아웃·본문·결론에서 반복한다면 한 곳에 설명을 모으고 필요한 곳에서는 짧게 연결한다. 제목은 해당 절의 내용을 찾을 수 있게 쓴다. 모든 제목을 “X — Y”나 질문형으로 맞추지 않는다.

문단은 한 역할을 충분히 수행하게 한다. 조건 제시, 관측, 인과 설명, 판단, 실행 지시를 필요에 따라 연결한다. 서로 의존하는 설명을 불릿 세 개로 쪼개지 말고 산문으로 이어 쓴다. 병렬 비교와 절차는 목록이나 표가 읽기 쉬우면 그대로 둔다. 한 문단 한 문장이나 매 절 세 문단을 목표로 삼지 않는다.

“핵심은”, “먼저”, “기준”, “한눈에”, “A가 아니라 B”를 새 동의어로 돌려 쓰지 않는다. 그 문장이 해야 할 일을 직접 쓴다. 추상적인 가치 판단을 덧붙이는 대신 기존 원문의 행동·결과·조건으로 표현한다. 문장 길이와 종결은 내용에 따라 달라지게 하되 원문의 문체를 불필요하게 뒤섞지 않는다.

측정값과 추정값, 문서에서 확인한 동작과 저자의 추론을 구분한다. “가능하다”를 “보장한다”로 바꾸거나, 특정 버전·리전·시점의 수치를 현재 일반값으로 만들지 않는다. 근거가 모호하면 원래의 제한을 유지하고 확인할 항목으로 보고한다. 사실 수정까지 필요할 때는 해당 주장에 필요한 출처를 확인한 뒤 수정 근거를 남긴다.

도입은 독자가 상황을 이해하는 데 필요한 만큼만 쓴다. 이미 제목과 첫 사례로 충분하면 개요를 추가하지 않는다. 마무리도 본문을 다시 요약하는 의무가 없다. 실제 다음 작업·적용 범위·남은 검증이 있으면 쓰고, 마지막 설명으로 끝나도 된다.

### 짧은 전후 예시

원문:

> 이 글에서는 보관 기간을 결정하는 세 가지 핵심 기준을 살펴봅니다.
> - **생성량**: 생성량을 확인하는 것이 중요합니다.
> - **보관**: 리플레이는 30일 뒤 삭제합니다.
> - **비용**: 리플레이는 장기 보관 비용에 누적되지 않습니다.
> 결론적으로 보관 정책을 잘 정하는 것이 핵심입니다.

편집:

> 리플레이를 30일 뒤 삭제한다면 저장량은 한 달치에서 안정됩니다. 보관 기간을 늘릴 때 추가되는 양은 삭제하지 않고 남겨 두는 다른 데이터에서 계산합니다.

반복 안내와 불릿 구성을 바꿨지만 30일 조건은 남겼다. 이 예시를 보고 실제 원문의 고유 수치·계산식·증거까지 생략해서는 안 된다. 예시의 문장 길이나 두 문장 구성도 규칙이 아니다.

## 실행 기록과 재개

새 구조 작업은 `_workspace/structure-{고유 실행 ID}/run.json`을 실제로 생성한다. 최초 파일을 편집하기 전에 `mode: "structure"`, `run_id`, `root`, `targets`, `apply_mode`(preview 또는 inplace), `status`, `updated_at`을 기록한다. `targets`는 파일마다 상대경로, 원본 스냅샷 경로, 원본 SHA-256, 후보 경로와 후보 SHA-256, 파일 상태를 담는다. 후보가 없으면 후보 경로/해시는 null로 둔다. 상태는 pending·editing·verified·applied·complete 중 진행 상황에 맞게 갱신한다. 검사·미리보기 결과로 완료한 경우 `apply_mode: "preview"`를 유지해 완료가 제자리 적용을 뜻하지 않게 한다.

파일 원본을 확보한 뒤 원본 경로와 digest를, 후보를 쓴 뒤 후보 경로와 digest를, 검증·적용을 마친 뒤 상태를 갱신한다. 검증 기록은 그때의 원본과 후보 digest에 연결한다. 이 정도의 JSON 기록으로 충분하며 별도 런타임이나 새 게이트 스크립트를 만들 필요는 없다. 처음 보관한 원본 증거는 재개하면서 덮어쓰지 않는다.

“지난 작업 이어서”는 명시된 run이나 현재 대화의 구조 작업을 이어받는다. 대화로 식별되지 않으면 이 기록과 보존 모드 `docs-*`를 함께 확인한다. 모드와 대상을 알 수 있는 run이 하나면 그대로 재개하고, 여러 run이 있어 어느 것인지 모호할 때만 묻는다. 구조 기록이 없더라도 대화에서 구조 작업임이 분명하면 그 모드를 유지하며 새 기록과 현재 원본을 확보한다. 보존 모드로 자동 전환하지 않는다.

재개 시 현재 대상의 digest를 원본과 비교하고 후보 digest도 기록과 대조한다. 원본이 달라졌거나 증거가 없으면 기존 후보·검증을 재사용하지 않는다. 현재 사용자 수정을 담은 새 작업 단위의 원본에서 후보를 다시 만든다. 후보만 달라졌으면 변경된 후보를 읽고 보존·렌더링 검증을 다시 수행한다. 이미 제자리 적용된 파일(applied 또는 inplace로 complete)은 적용된 후보 digest와 현재 파일을 대조해 상태만 보고하며, 새 수정 요청 없이 다시 덮어쓰지 않는다. preview로 complete인 파일은 현재 원본을 원본 digest와 대조하며 제자리 적용됐다고 간주하지 않는다. 명시적 콜/비용 예산은 재개나 새 작업 단위에서도 누적해 지킨다. 한도 때문에 새 후보를 만들 수 없으면 미완료 사유를 남기고 낡은 후보는 적용하지 않는다.

원본 변경·증거 부족에 따른 **새 작업 단위는 변경된 대상만 포함하는 새 구조 run**으로 기록한다. 새 run의 `supersedes`에 이전 run ID와 대상 경로를 남기고, 이전 대상에는 `superseded_by`로 새 run ID를 적어 자동 재개·적용에서 제외한다. 이전 스냅샷과 digest는 보존한다. 새 run은 현재 원본 스냅샷·digest를 기준으로 검증·적용하며, 다른 미변경 대상은 이전 run에서 계속 처리한다. 편집자·편집 범위·적용 방식과 누적 호출·비용은 이어받고 한도를 초기화하지 않는다. 새 run을 만들 수 없는 예산 상태라면 이전 후보를 적용하지 않고 미완료로 보고한다.

## 보존해야 하는 내용과 별도 후보

편집 전에 대상 목록과 현재 파일을 보관하고 후보를 별도 경로에 작성한다. 위 실행 디렉토리 아래 원본·후보·짧은 편집 메모를 두고 `run.json`에서 참조한다. 저장소 상대경로를 유지해 같은 이름의 파일이 충돌하지 않게 한다. 기존 `docs-*` run의 `options.env`·`candidate.path`를 가져오지 않는다. 새 요청에 낡은 보존 모드 결과를 자동 적용하지 않는다.

원본 보관은 현재 작업 트리 기준이다. 이미 있던 사용자 수정도 포함하고 `git show HEAD`만을 원본으로 취급하지 않는다. 후보 적용 직전에 현재 파일과 보관한 원본을 대조한다. 다른 변경이 들어왔다면 위 재개 규칙에 따라 현재 원본에서 새 후보를 만들고 검증한다. 적용 직전의 원본 대조가 실패하면 verified 상태여도 덮어쓰지 않는다.

코드·명령·설정 키·URL·출처·이미지와 shortcode·frontmatter·고유 수치와 단위·인용의 의미를 보존한다. 코드 블록은 내용 그대로 이동할 수 있다. 중복을 줄여도 유일한 근거와 단정의 전제·예외를 삭제하지 않는다. 같은 URL을 여러 번 썼다면 참조 횟수는 줄일 수 있지만 필요한 출처 연결은 남긴다. 경험·측정·사례·인용을 새로 만들지 않는다.

헤딩·문단·목록·표의 형태는 바꿀 수 있다. 표를 풀어 쓸 때는 모든 비교 조건과 값을 후보에 남긴다. 파일 경로와 frontmatter 변경은 구조 편집에서 자동으로 허용되는 작업이 아니다. 사용자가 따로 요청하지 않았다면 유지한다.

## 재작성 후보를 검증하는 방법

원본과 후보를 각각 읽어 대조한다. 후보만 자연스럽게 읽힌다고 보존 검증을 마치지 않는다.

1. **내용 대조:** 주요 주장·근거·전제·예외가 후보의 어디에 남았는지 확인한다. 삭제한 절은 중복이었는지, 다른 절로 옮겼는지 짧게 기록한다. 새 문장은 원문에서 도출되는 설명인지 확인한다.
2. **자산 대조:** 코드 블록과 frontmatter의 원문 일치, 수치·단위·식별자 보존, 출처 URL 및 이미지·shortcode 대상 누락을 검사한다. 의도적으로 바뀐 항목은 근거를 별도로 보고한다. 순서 변경이 허용된 자산은 위치가 아니라 내용과 참조 관계를 비교한다.
3. **링크와 렌더링:** 실제 저장소 렌더러로 후보를 빌드한다. 헤딩을 바꿨다면 이전 렌더링의 ID와 새 ID를 비교하고, 기존 공개 딥링크는 명시적 앵커 등 프로젝트가 지원하는 방법으로 보존한다. 저장소 전체에서 같은 파일과 다른 파일을 향하는 내부 링크·fragment·relref·aliases·이미지 경로를 확인한다. 옮긴 절로 향하는 링크도 새 위치를 가리키게 한다.
4. **읽기 검토:** 글의 질문에 답하는 순서인지, 근거보다 단정이 앞서 나가는지, 시리즈 모든 글이 또 같은 서론과 결론을 갖게 됐는지 확인한다. 필요한 부분을 다시 편집한 뒤 영향을 받은 검증을 반복한다.

`heading_anchor.py`는 GitHub 방식의 slug와 같은 파일 내부 링크를 다룬다. 이 결과로 Hugo/Goldmark 등 다른 렌더러의 앵커나 저장소 전체 링크를 검증했다고 보고하지 않는다. 원본과 후보를 별도 출력 디렉토리에서 빌드하거나 프로젝트의 기존 미리보기 방법을 사용한다. 렌더러 실행이 막히면 가능한 정적 대조를 수행하고 미검증 범위를 밝힌다.

`md_shield.py verify`의 헤딩·목록 보존 게이트는 이 후보의 합격 판정이 아니다. 이를 통과시키기 위해 후보 헤딩을 원문으로 복원한 사본을 검증하고 실제 후보가 통과했다고 말하지 않는다. `llm_signature.py`, `author_repeat.py`, `slop_scan.py`는 필요한 경우 진단에만 쓴다. 점수 감소나 exit 0은 논증·사실·링크의 정확성을 증명하지 않는다.

## 적용과 보고

사용자가 지정 파일을 다시 쓰거나 수정하라고 이미 요청했다면 그것이 해당 범위의 로컬 편집 권한이다. 후보와 검증을 준비한 뒤 적용하며 “진행할까요”를 다시 묻지 않는다. 미리보기·평가만 요청했다면 후보나 평가만 전달한다. “구조 재작성 + 미리보기만”은 구조 후보 생성과 검증까지 수행하되 원본 적용은 하지 않는다. 최신 요청의 미리보기 제한은 이전 적용 허용보다 우선한다. 새로운 사실 결정, 범위 밖 파일 이전·삭제, 외부 게시처럼 별도 판단이 필요한 일은 독립적으로 구분한다.

마지막에는 변경한 파일, 바꾼 전개와 이유, 보존 대조 결과, 실행한 빌드·링크 검사, 남은 불확실성을 짧게 보고한다. 완료 조건은 요청한 모든 글을 실제로 다시 검토·편집하고 필요한 보존·렌더링 검증을 마치는 것이다. 지문 등급이나 글자 수 감소를 완료 조건으로 삼지 않는다.
