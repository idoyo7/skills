# 마이크로서비스 환경에서의 분산 트레이싱 도입기

우리 팀은 최근 몇 달간 마이크로서비스 아키텍처로의 전환을 진행하면서, 서비스 간 호출 관계가 복잡해짐에 따라 발생하는 여러 가지 문제들에 직면하게 되었습니다. 특히 하나의 사용자 요청이 여러 개의 서비스를 거쳐 처리되는 과정에서, 어느 지점에서 지연이 발생하는지를 파악하는 것이 매우 어려운 과제로 다가왔습니다. 이러한 문제를 해결하기 위해 우리는 분산 트레이싱(distributed tracing) 시스템을 도입하기로 결정하였으며, 본 문서에서는 그 과정에서 얻은 인사이트와 경험을 공유하고자 합니다.

## 왜 분산 트레이싱이 필요한가

기존의 모놀리식 애플리케이션에서는 로그 하나만 살펴보아도 요청의 전체 흐름을 파악하는 것이 상대적으로 용이했습니다. 하지만 마이크로서비스 환경으로 전환하면서 상황이 완전히 달라졌습니다. 하나의 요청이 API 게이트웨이를 거쳐 인증 서비스, 사용자 서비스, 주문 서비스, 결제 서비스 등 여러 서비스를 순차적으로 혹은 병렬적으로 호출하게 되었고, 이 과정에서 발생하는 지연이나 에러를 추적하는 것이 상당히 까다로워졌습니다.

이는 단순히 로그를 각 서비스별로 모아본다고 해결되는 문제가 아니었습니다. 왜냐하면 각 서비스의 로그에는 요청 간의 인과관계에 대한 정보가 담겨 있지 않았기 때문입니다. 따라서 우리는 요청 전체에 걸쳐 고유한 식별자(trace ID)를 부여하고, 각 서비스 호출을 하나의 스팬(span)으로 기록하여 전체 흐름을 시각화할 수 있는 도구가 필요하다는 결론에 도달하게 되었습니다.

### 도입 전 검토했던 옵션들

| 솔루션 | 특징 | 검토 결과 |
|---|---|---|
| Jaeger | CNCF 프로젝트, 성숙도 높음 | 후보 |
| Zipkin | 오래된 프로젝트, 커뮤니티 활발 | 제외(신규 기능 둔화) |
| Tempo | Grafana 생태계와 통합 용이 | 최종 선택 |
| AWS X-Ray | 관리형, 벤더 종속 | 제외(멀티 클라우드 요건) |

여러 옵션들을 비교 검토한 결과, 우리는 최종적으로 Grafana Tempo를 선택하게 되었습니다. 그 이유는 다음과 같습니다. 첫째, 이미 우리 팀에서 Grafana를 메트릭 대시보드 용도로 사용하고 있었기 때문에 추가적인 학습 비용이 적었습니다. 둘째, 오브젝트 스토리지를 백엔드로 사용할 수 있어 비용 효율적인 장기 보관이 가능했습니다. 셋째, OpenTelemetry와의 호환성이 뛰어나 향후 계측 코드를 표준화하는 데 유리했습니다.

## 계측(instrumentation) 적용 과정

계측을 적용하는 과정에서 가장 중요하게 고려했던 부분은 애플리케이션 코드에 대한 침습성을 최소화하는 것이었습니다. 이를 위해 우리는 OpenTelemetry의 자동 계측(auto-instrumentation) 기능을 최대한 활용하였고, 필요한 경우에 한해서만 수동으로 스팬을 추가하는 방식을 채택하였습니다.

```go
tracer := otel.Tracer("주문서비스")
ctx, span := tracer.Start(ctx, "주문생성")
defer span.End()

span.SetAttributes(
    attribute.String("주문.id", orderID),
    attribute.Int("주문.상품수", len(items)),
)
```

위 코드 예시에서 볼 수 있듯이, 스팬에는 비즈니스 로직과 관련된 속성(attribute)들을 추가하여 나중에 문제를 진단할 때 유용한 정보로 활용할 수 있도록 하였습니다. 이러한 접근 방식은 단순히 기술적인 지표만을 수집하는 것이 아니라, 비즈니스 맥락을 함께 담아냄으로써 트레이스 데이터의 활용도를 크게 높일 수 있었습니다.

### 샘플링 전략

전체 트래픽에 대해 100% 트레이싱을 수행하는 것은 저장 비용과 성능 오버헤드 측면에서 현실적이지 않았습니다. 이에 우리는 다음과 같은 샘플링 전략을 수립하였습니다.

1. 에러가 발생한 요청은 항상 100% 샘플링한다
2. 지연 시간이 임계값(예: 1초)을 초과하는 요청은 항상 샘플링한다
3. 나머지 정상 요청에 대해서는 1%의 비율로 샘플링한다
4. 특정 VIP 고객의 요청은 별도로 10% 샘플링한다

이러한 tail-based sampling 전략을 적용함으로써, 저장 비용을 크게 절감하면서도 문제 진단에 필요한 데이터는 놓치지 않을 수 있었습니다. 물론 이를 구현하기 위해서는 OpenTelemetry Collector의 tail sampling processor를 별도로 운영해야 했으며, 이 과정에서 몇 가지 운영상의 어려움을 겪기도 하였습니다.

## 도입 후 얻은 효과

분산 트레이싱을 도입한 이후, 우리 팀은 장애 대응 시간(MTTR)이 눈에 띄게 단축되는 효과를 경험하였습니다. 이전에는 여러 서비스의 로그를 일일이 대조하며 문제의 원인을 찾아야 했지만, 이제는 트레이스 하나만 열어보면 전체 요청의 흐름과 각 구간별 소요 시간을 한눈에 파악할 수 있게 되었습니다.

> 핵심은 이것입니다: 트레이싱은 "무엇이 느린가"를 답해주는 도구이지, "왜 느린가"까지 자동으로 답해주지는 않습니다. 그럼에도 불구하고 원인 파악의 범위를 극적으로 좁혀준다는 점에서 그 가치는 명확합니다.

결론적으로, 마이크로서비스 아키텍처로의 전환을 고려하고 있는 팀이라면 분산 트레이싱 도입을 초기 단계부터 함께 계획하는 것을 강력히 권장합니다. 나중에 추가하려고 하면 계측 코드를 전체 서비스에 걸쳐 소급 적용해야 하는 부담이 훨씬 커지기 때문입니다.
