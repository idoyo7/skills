# API 레이트 리미팅 도입 가이드

레이트 리미팅은 서비스 안정성을 지키기 위한 핵심 장치입니다. 이 문서는 도입 시
고려해야 할 사항을 정리합니다.

## 알고리즘 선택 🚀

레이트 리미팅에는 여러 알고리즘이 있으며 각각 장단점이 있습니다.

- **토큰 버킷**: 버스트 트래픽을 어느 정도 허용하는 방식입니다
- **고정 윈도우**: 구현이 가장 간단하지만 경계에서 트래픽이 몰릴 수 있습니다
- **슬라이딩 윈도우**: 정확도가 높지만 메모리 비용이 더 듭니다

## 저장소 선택 📌

상태를 어디에 저장할지도 중요한 결정입니다.

- **Redis**: 대부분의 서비스에서 표준적으로 선택하는 저장소입니다
- **로컬 메모리**: 단일 인스턴스 환경에서만 유효합니다
- **DynamoDB**: 완전 관리형이 필요할 때 고려합니다

⚠️ **주의**: 분산 환경에서 로컬 메모리 카운터를 쓰면 리밋이 사실상 무력화됩니다.

## 응답 설계

리밋에 걸렸을 때 클라이언트에게 무엇을 돌려줄지도 설계가 필요합니다.

- **상태 코드**: 429 Too Many Requests를 사용합니다
- **재시도 안내**: Retry-After 헤더로 대기 시간을 알려줍니다
- **로깅**: 리밋 발생 빈도를 모니터링에 남깁니다

---

## 정리

이 문서에서는 레이트 리미팅 알고리즘 선택, 저장소 선택, 응답 설계 세 가지를
정리합니다.

- **알고리즘 선택**: 토큰 버킷이나 슬라이딩 윈도우를 서비스 특성에 맞게 선택합니다
- **저장소 선택**: 분산 환경에서는 Redis를 표준적으로 선택합니다
- **응답 설계**: 상태 코드 429와 Retry-After 헤더로 재시도 안내를 합니다

레이트 리미팅 알고리즘, 저장소, 응답 설계 세 가지를 함께 고려하는 것이
중요합니다.
